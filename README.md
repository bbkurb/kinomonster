# КиноМонстр

Сайт о кино на **CodeIgniter 4.7.4**. Перенесён с CodeIgniter 3.1.8 — старая
версия полностью переписана, а не обновлена (CI4 несовместим с CI3).

---

## Быстрый запуск в Laragon

### Что нужно заранее

| Требование | Как проверить |
|---|---|
| PHP **8.2+** | меню Laragon → *PHP* → *Version* |
| Расширение **intl** | меню → *PHP* → *Extensions* → должна стоять галочка `intl` |
| Расширение **mbstring** | там же |
| MySQL / MariaDB | запускается вместе с Laragon |

Без `intl` CodeIgniter 4 **не запустится вообще** — это первое, что стоит проверить,
если увидите ошибку при старте.

### Шаг 1. Положить проект в правильное место

Папка проекта должна лежать **отдельным каталогом** внутри `www`:

```
C:\laragon\www\kinomonster\
```

Проверьте, что внутри есть **4 папки и 6 файлов**:

```
app\  public\  system\  writable\
.gitignore  LICENSE  README.md  composer.json  env.example  spark
```

Ключевой признак, что скопировалось всё: существует файл
`C:\laragon\www\kinomonster\public\index.php`.

> **Важно.** Не копируйте содержимое проекта прямо в `C:\laragon\www\` —
> Laragon покажет список файлов вместо сайта. Проект должен быть в своей папке.

### Шаг 2. Создать базу данных

Откройте **HeidiSQL** (идёт в комплекте с Laragon) и создайте базу с именем
`kinomonster` и кодировкой `utf8mb4_general_ci`.

Либо через терминал Laragon (меню → *Terminal*):

```bash
mysql -u root -e "CREATE DATABASE kinomonster CHARACTER SET utf8mb4"
```

### Шаг 3. Перезапустить Laragon

Нажмите **Stop**, затем **Start**.

При старте Laragon сканирует папки в `www`, видит внутри проекта каталог
`public/` и **сам** делает его корнем сайта. Отдельно настраивать
виртуальный хост не нужно.

Сайт открывается по адресу: **http://kinomonster.test**

### Шаг 4. Создать таблицы и заполнить данными

В терминале Laragon перейдите в папку проекта и выполните:

```bash
cd C:\laragon\www\kinomonster

php spark migrate
php spark db:seed DemoSeeder
```

Первая команда создаёт таблицы, вторая — наполняет сайт примерами
(8 фильмов и сериалов, новости, посты) и создаёт учётные записи:

| Логин | Пароль | Роль |
|---|---|---|
| `admin` | `admin12345` | администратор |
| `vasya` | `vasya12345` | обычный пользователь |

Обе команды безопасно запускать повторно — данные не задублируются.

Готово. Открывайте **http://kinomonster.test** и входите как `admin`.

## Если что-то пошло не так

**Вместо сайта — список файлов (`Index of /`)**
Корень сайта указывает не туда. Проект должен лежать в отдельной папке
`C:\laragon\www\kinomonster\`, а не прямо в `www`. После перемещения —
перезапустите Laragon.

**`Not Found` при открытии `/public`**
Папка `public` не скопировалась. Проверьте, что файл
`public\index.php` существует; если нет — скачайте проект заново
(при копировании потерялись папки).

**Ошибка про `intl`**
Меню Laragon → *PHP* → *Extensions* → включить `intl` → перезапустить.

**`Unable to connect to the database`**
База `kinomonster` не создана (шаг 2) либо у MySQL задан пароль для `root`.
Во втором случае скопируйте `env.example` в `.env` и впишите пароль:

```bash
copy env.example .env
```

**Белая пустая страница**
Обычно означает фатальную ошибку PHP. Загляните в `writable\logs\` —
там лежит подробный лог. По умолчанию проект запускается в режиме
`development`, поэтому текст ошибки должен выводиться прямо в браузер.

**Сайт открыт как `localhost/kinomonster/public`**
Так тоже работает: адреса ссылок и картинок определяются автоматически.
Но `http://kinomonster.test` удобнее и ближе к боевым условиям.

## Развёртывание на боевом сервере

1. Корень сайта (DocumentRoot) направить на папку **`public`**, а не на корень проекта.
2. Скопировать `env.example` в `.env`, указать реальные доступы к базе и
   поставить `CI_ENVIRONMENT = production`.
3. Выполнить `php spark migrate`.
4. **Не запускать** `db:seed DemoSeeder` — он создаёт тестовых пользователей
   с общеизвестными паролями.
5. Папка `writable/` должна быть доступна веб-серверу на запись.

### Перенос существующего сайта с CI3

Миграции рассчитаны на обе ситуации. Если база уже есть от старой версии,
таблицы не пересоздаются — добавляются только недостающие колонки
(`role`, `reset_key`, `reset_expires`, `activated`, `created_at`),
администраторы переносятся из таблицы ролей DX_Auth в колонку `users.role`,
создаются индексы.

**Пароли существующих пользователей продолжают работать.** DX_Auth в поздних
версиях уже использовал `password_hash()` с bcrypt; такие хеши принимаются и
незаметно обновляются до актуального алгоритма при первом входе.

Старые таблицы DX_Auth (`roles`, `permissions`, `user_temp` и прочие) не
удаляются автоматически — команды для ручной очистки приведены в комментарии
в конце файла `app/Database/Migrations/..._AddUserAuthColumns.php`.
Сделайте резервную копию базы перед этим.

## Структура проекта

```
app/
  Config/       настройки (маршруты, база, фильтры)
  Controllers/  контроллеры
  Models/       модели
  Services/     сервис аутентификации
  Filters/      проверка прав доступа
  Views/        шаблоны
  Database/     миграции и сидеры
public/         ← корень сайта: index.php, assets/
system/         фреймворк CodeIgniter 4
writable/       логи, кеш, сессии
```

### Что изменилось по сравнению с версией на CI3

| CI3 | CI4 |
|---|---|
| `application/controllers/` | `app/Controllers/` |
| `application/models/Films_model.php` | `app/Models/FilmsModel.php` |
| `application/libraries/Dx_auth.php` (2365 строк) | `app/Services/Auth.php` (~280 строк) |
| `application/core/MY_Controller.php` | `app/Controllers/BaseController.php` |
| проверки прав внутри методов | фильтры `auth` / `admin` на маршрутах |
| `index.php` в корне | `public/index.php` |

### Исправленные уязвимости

Каждый пункт менял реальное поведение приложения:

- **Комментарий от чужого имени.** `user_id` приходил скрытым полем формы, и
  сервер ему доверял. Теперь берётся из сессии.
- **CSRF-защиты не было вообще.** Сторонняя страница могла отправить от имени
  залогиненного администратора запрос на удаление. Включена глобально.
- **Удаление по обычной ссылке.** `/movies/delete/matrix` срабатывал по GET —
  запись мог удалить поисковый робот. Переведено на POST.
- **`javascript:` в ссылке на плеер** попадал в `src` iframe и выполнялся у
  каждого посетителя. Добавлена проверка схемы URL.
- **Предсказуемые токены.** Ключи активации и сброса генерировались как
  `md5(rand() . microtime())`. Заменено на `random_bytes(32)`, в базе хранится
  SHA-256, срок жизни — 1 час.
- **Неограниченный перебор паролей.** Добавлен лимит: 5 попыток / 15 минут.
  Сообщение об ошибке одинаково для несуществующего логина и неверного пароля.
- **XSS в поиске** через `http_build_query($_GET)` в ссылках пагинации.

Плюс исправлены: N+1 запрос в комментариях (100 запросов → один JOIN),
подсчёт длины русских названий через `strlen()` вместо `mb_strlen()`,
потеря отзыва при сбое отправки почты и опечатка `__constract` в двух
контроллерах, из-за которой конструктор никогда не вызывался.
