# КиноМонстр — версия на CodeIgniter 4

Перенос сайта с CodeIgniter 3.1.8 на CodeIgniter 4.7.4.

CI4 — не обновление CI3, а другой фреймворк, поэтому код переписан, а не
сконвертирован. Старая версия осталась нетронутой в каталогах `application/`
и `system/` в корне репозитория — их можно удалить после того, как новая
версия будет проверена на боевых данных.

## Требования

| Что | Версия |
|---|---|
| PHP | 8.2 или новее |
| Расширения | `intl`, `mbstring`, `json`, `mysqlnd` |
| MySQL | 5.7+ / MariaDB 10.3+ |

`intl` обязателен — без него CI4 не стартует.

## Установка

```bash
cd ci4
composer install          # если используете Composer-вариант
cp env .env               # и отредактируйте
```

Минимум, что нужно указать в `.env`:

```ini
CI_ENVIRONMENT = production

app.baseURL = 'https://ваш-домен/'

database.default.hostname = localhost
database.default.database = kinomonster
database.default.username = ваш_пользователь
database.default.password = ваш_пароль
database.default.DBDriver = MySQLi

email.fromEmail = noreply@ваш-домен
email.adminEmail = info@ваш-домен
```

Корень сайта (DocumentRoot) должен указывать на `ci4/public`, а не на `ci4`.
Это принципиальное отличие от CI3: код приложения теперь лежит выше
директории, доступной из веба.

## Миграция базы

```bash
php spark migrate
```

Миграции добавляют в таблицу `users` колонки `role`, `reset_key`,
`reset_expires`, `activated`, `created_at`, переносят администраторов из
таблицы `roles` DX_Auth в новую колонку `role` и создают индексы под запросы
главной страницы, рейтинга и поиска.

Старые колонки и таблицы DX_Auth не удаляются — список команд для ручной
очистки приведён в конце файла миграции `..._AddUserAuthColumns.php`.

**Пароли существующих пользователей продолжают работать.** DX_Auth в поздней
версии уже использовал `password_hash()` с bcrypt; `UserModel::verifyPassword()`
принимает такие хеши и незаметно перехеширует их в актуальный алгоритм при
первом успешном входе.

## Что изменилось в структуре

| CI3 | CI4 |
|---|---|
| `application/controllers/Movies.php` | `app/Controllers/Movies.php` |
| `application/models/Films_model.php` | `app/Models/FilmsModel.php` |
| `application/libraries/Dx_auth.php` (2365 строк) | `app/Services/Auth.php` (~280 строк) |
| `application/core/MY_Controller.php` | `app/Controllers/BaseController.php` |
| `application/helpers/other_helper.php` | `app/Helpers/menu_helper.php` |
| проверки прав внутри методов | фильтры `auth` / `admin` в `Config/Routes.php` |
| `$this->load->view()` × 3 | `BaseController::renderPage()` |
| разметка пагинации в контроллерах | `app/Views/pager/bootstrap.php` |

## Исправленное при переносе

Это не косметика — каждый пункт менял поведение приложения.

**Комментарий от чужого имени.** Форма комментария передавала `user_id`
скрытым полем, и сервер ему доверял. Любой залогиненный пользователь мог
подменить значение и оставить отзыв от имени другого. Теперь id берётся из
сессии, из формы поле убрано.

**Отсутствие CSRF-защиты.** В CI3 она не была включена вообще: любая внешняя
страница могла отправить от имени залогиненного админа запрос на удаление
фильма. Сейчас фильтр `csrf` включён глобально, во всех формах — `csrf_field()`.

**Удаление по GET-ссылке.** `/movies/delete/matrix` работал по обычному клику,
то есть запись мог удалить поисковый робот или предзагрузка ссылки в браузере.
Удаление переведено на POST с подтверждением.

**`javascript:` в ссылке на плеер.** Значение поля подставлялось в `src`
`<iframe>` без проверки схемы, что давало выполнение произвольного скрипта у
каждого посетителя. Добавлены правило валидации `safe_media_url` и хелпер
`safe_url()` в шаблонах.

**Небезопасные токены.** Ключи активации и автологина генерировались как
`md5(rand() . microtime())` — предсказуемо. Теперь `random_bytes(32)`, в базе
хранится SHA-256 от ключа, срок жизни — 1 час, сравнение через `hash_equals()`.

**Перебор паролей.** Ограничений на попытки входа не было. Добавлен лимит:
5 неудач — блокировка на 15 минут. Сообщение об ошибке одинаково для
несуществующего логина и неверного пароля, чтобы нельзя было перебором
собрать список пользователей.

**Утечка XSS в поиске.** Строка запроса склеивалась вручную через
`http_build_query($_GET)` и попадала в ссылки пагинации без экранирования.
Заменено штатным Pager.

**N+1 запрос в комментариях.** Шаблон вызывал `getUserNameByID()` на каждый
комментарий — 100 комментариев давали 100 отдельных запросов. Теперь один JOIN.

**Обрезка русских названий.** `strlen()` на UTF-8 считает байты, поэтому
кириллические названия обрезались вдвое раньше. Везде `mb_*`.

**Потеря обратной связи.** При сбое отправки почты сообщение пропадало.
Теперь оно сначала пишется в БД, потом отправляется письмо.

**Опечатка `__constract`.** В `Main.php` и `Movies.php` конструктор был назван
с ошибкой, из-за чего не вызывался никогда, а `Movies` не загружал свою модель
в конструкторе. Исправлено.

## Что убрано осознанно

- **reCAPTCHA** — ключи были захардкожены в конфиге и давно недействительны;
  её роль (защита от перебора) закрыта лимитом попыток входа.
- **Таблицы ролей и прав DX_Auth** (`roles`, `permissions`, `uri_permissions`) —
  реально использовались две роли, они свелись к колонке `users.role`, а права
  на маршруты задаются фильтрами.
- **`Auth::custom_permissions()`** — печатал отладочный текст прямо в браузер.
- **Автороутинг** — выключен. Все маршруты объявлены явно в `Config/Routes.php`,
  попасть в метод контроллера в обход фильтров нельзя.

## Проверка

Код прогонялся в песочнице на PHP 8.5 с тестовой базой SQLite:

- 104 PHP-файла — без синтаксических ошибок;
- 26 проверок моделей (хеши, ключи сброса, выборки, валидация);
- 26 проверок сервиса `Auth` (вход, роли, троттлинг, смена пароля);
- 18 HTTP-маршрутов (14 публичных → 200, 4 закрытых → 404);
- 10 проверок разграничения доступа (аноним / user / admin);
- 4 проверки CSRF на всех POST-эндпоинтах;
- 6 проверок совместимости со старой базой DX_Auth.

**Что не проверялось и требует внимания при развёртывании:** работа на MySQL
(тесты шли на SQLite — синтаксис Query Builder одинаков, но стоит прогнать
миграции на копии боевой базы), реальная отправка почты и поведение под
`intl`, которого в песочнице не было.
